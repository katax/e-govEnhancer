# 通常モードの法令読み込み・加工キャッシュ：追加調査

調査日：2026-10-16（日本時間）／拡張機能 2.6.2／HEAD `bb84aa6`（`Add optional external file sync`）。

## 結論

定義辞書と同一法令内の逆参照関係は保存できる。ただし、現在のDOM依存処理をそのまま保存する前に、**版・本文・表示モードの識別、附則を含む条項キー、解析中断とDOM再結合**を整える必要がある。加工済みHTMLの丸ごと保存は推奨しない。

今回、現コードの再照合、実サイトでの現行版・過去版・条文比較表示の観察、現ソースから切り出した関数の8件の再現検証、既存Lite読み込みテスト7件の実行まで行った。製品コードは変更していない。速度改善率、拡張機能を入れた実ブラウザでの加工時間、IndexedDBとメッセージ転送の実費用は未測定。

## 2. 実ページで新たに確認できたこと

対象は [行政手続法の通常表示](https://laws.e-gov.go.jp/law/405AC0000000088)。以下は法律の内容に関する判断ではなく、表示構造と版識別の観察である。

### 2.1 改正IDは画面から取得できる候補がある

画面上の `div.revisionid` に `Law RevisionID:...` が表示されていた。現行URLには改正IDがないが、表示ラベルには解決済みの改正IDがある。

| 観察項目 | 現行表示 | 履歴から選んだ過去表示 |
|---|---|---|
| 画面の改正ID | `405AC0000000088_20260724_508AC0000000066` | `405AC0000000088_20240401_504AC0100000052` |
| URL | `/law/405AC0000000088` | `/law/405AC0000000088/20240401_504AC0100000052?occasion_date=20240401` |
| 現コードで得る条文数 | 48 | 48 |
| 先頭／末尾ID | `Mp-Ch_1-At_1`／`Mp-Ch_7-At_46` | 同じ |
| 再適用署名 | `48:Mp-Ch_1-At_1:Mp-Ch_7-At_46` | 同じ |
| `#provisionview a[href]` の数 | 172 | 166 |

**異なる版・異なるリンク構成を、現署名が識別できないことを実ページで確認した。** これは署名の衝突を確認したものであり、この操作で拡張機能の表示不良まで再現したという意味ではない。調査用ブラウザに拡張機能は入っていない。

改正IDラベルは実装候補に使える。ただしサイト側の非公開DOM仕様であり、安定した公式インターフェースとは断定できない。複数候補・非表示ラベル・本文更新中のラベル先行表示を考慮する。URLとラベルを別々に保存し、ラベルだけで本文完成を判定しない。

### 2.2 本体は独自の内部APIを利用している

ページ資材一覧で次のリソースを観測した。

```text
/internal-api/SelectLawRevisionData.json
/internal-api/SelectLawTocData.json
/internal-api/SelectLawData.json
/internal-api/SelectLawTextData.json
```

Liteの `background.js:822`・`shared/egov-shared.js:1166` が使う公開 `/api/2/law_revisions/`・`/api/2/law_data/` とは異なる経路である。通常モードの本文は本体側で構築され、拡張は `document_end` から後加工する。この構造上、加工キャッシュだけでは本体の通信・描画を省略できない。

資材一覧は複数画面の累積情報である。HTTPメソッド、要求本文、応答構造、画面ごとの要求数、キャッシュヘッダーまでは取得していない。内部API名を、実装で依存してよい公開契約とは扱わない。

公式の[法令API Version 2](https://laws.e-gov.go.jp/api/2/swagger-ui)では公開APIの履歴取得と本文取得が案内されている。今回確認した資料から、同一改正IDの内容が永久に不変という保証は得られていない。内容ハッシュを省く根拠はない。

### 2.3 版ラベル表示と本文完成は同時とは限らない

過去版の履歴ボタンを選択した直後のDOMスナップショットでは、過去版の改正IDと法令名が表示され、条文本文はまだ現れていなかった。後の観察で48条文を確認した。時刻付きトレースではないため、この差の所要時間は分からない。

`waitForArticles()`（`content.js:2690`）は最初の条文が見つかれば成功する。`window.load` と最初の条文の存在だけを「全文完成」の条件にしない。今回の観察だけでは、逐次ロードする条文単位や本体の完了通知までは特定できていない。

### 2.4 条文比較は通常本文と同じ入力ではない

同じ過去版で「条文比較」を選ぶと、URLに `tab=compare` が付き、現行の `getAllArticles()` のセレクターに合う条文は0件、本文中のリンクは0件だった。同時に `Mp-Ch_1-At_3` というID値の重複が見つかった。

これは本文ゼロの通常法令として保存すべき状態ではない。初期実装では通常の「条文」表示のみを対象とし、比較表示への切替で実行中の解析・適用を取り消す設計がよい。比較表示用の解析を将来作る場合は、別の入力形式・左右の文脈・キーを持たせる。

過去版の通常表示では候補セレクターに合う非表示要素は0件だった。非表示の改正履歴が常に混入するとは確認できていない。

## 3. 現コードの再現検証で絞り込めた注意点

| 項目 | 確認した挙動 | 意味・限界 |
|---|---|---|
| 附則scopeの欠落 | `parseProvisionPath()`（content 3862）はscopeを返さず、`buildJumpHistoryKey()`（1862）もscopeを含めない。本則と附則の第2条第1項第3号の2がともに `2.1.3_2` | 定義の表示キー・再結合キーとして不十分。現在のジャンプは保持中のElementも使うため、直ちに全ジャンプが誤るという意味ではない |
| 定義候補の混在 | `buildDefinitionCandidateCache()`（4214）がarticle値だけでまとめ、本則と附則の同じ条番号が同一グループになる | 最短の一致候補が別scopeから選ばれ得る。具体的な法令での誤選択は未再現 |
| 再適用署名 | 条文数と先頭・末尾IDが同じなら、本文・href変更後も同じ値 | 永続キーとして流用不可。現行の再実行抑止にも同じ制約がある |
| 変更監視 | controller 44は `childList/subtree` のみ。本文内部の文字変更・href変更だけでは監視されない | 属性監視を足すだけでは自己加工と区別できない。入力世代の設計が必要 |
| 空の条文一覧 | `getAllArticles()`（5812）は空配列も保持し、DOMに条文が出現しても明示的な無効化までは空のまま | 別の監視で無効化する統合経路があるため、通常動作で必ずタイムアウトするとは断定しない。`waitForArticles`単独の完了判定には使いにくい |
| HTML復元とイベント | shared 760は `data-egov-reference-bound=true` があるとイベントを登録しない | HTMLだけ復元し属性を残すと、WeakMapの再登録後もクリック・キーボードのイベント登録が0件になる |
| 内部参照元URL | shared 367の生成URLは `/law/{lawId}#...` で、選択中の過去版文脈を持たない | 過去版由来の解析を保存してもリンク先は版固定にならない。版を含む移動方針を先に決める |
| 待機中の無効化 | `applyDefinitionTooltips()`（4519）は `await waitForArticles()` の後で有効設定を再確認しない。待機中にOFFにしても抽出・markが実行される | 最小代替環境で再現。画面差替え・トグル・本文世代を確認してから適用する必要がある |

附則の共通パーサー `parseProvisionHash()`（`shared/egov-shared.js:82`）はscopeを保持するため、共通のscope付きキーへ寄せる入口は既にある。ただし通常モードの既存キーと保存済み個人データの互換性は別途維持する。

なお、`content.js:7485` の本文変更時の経路には定義、ハイライト、ブックマーク再適用があり、内部逆参照再収集はない。外部参照の取得結果にもデータ世代は付かない（shared 1254）。これらは静的再確認である。

## 4. 加工処理ごとの保存方針

| 処理 | 保存するとしたら何か | 毎回必要な部分／無効化条件 | 優先度 |
|---|---|---|---|
| 定義抽出 A/B/C/D | 用語・定義文・scope付き出典キー・出典種別 | 現DOMとの結合。本文・可視対象・抽出規則変更で失効 | 高 |
| 定義の出現検索 | 条項内の基準文字位置 | 除外箇所・境界・一致文字列検証とspan作成。ノード番号は保存しない | 計測後 |
| 内部逆参照 | targetKey→参照元情報のJSON | DOM索引・クリック化。本文・リンク・構造・URL解釈の変更で失効 | 高 |
| 外部逆参照 | 既存の法令単位IndexedDB結果 | 取込／同梱データ世代で失効。既にキャッシュあり | 世代管理を追加 |
| 内外逆参照の統合 | 必要なら統合JSON | 内部本文世代と外部データ世代に依存。通常はメモリで十分か測定 | 中 |
| 条項索引・本文整形 | scope付き構造・正規化テキスト | Element結合。本文・構造・ルビ・改行規則に依存 | 高、共有を優先 |
| 括弧の範囲・深さ | 基準テキスト中の範囲 | spanとグループMapを再作成。初回操作時に動くため通常初期表示への効果は限定 | 計測後 |
| 漢数字・かな変換 | 基準本文からの変換差分 | 表示本文と位置対応の再構築。通常の初期処理ではない | 低 |
| 検索 | 基準検索テキスト | 現DOMのsegments・Range・CSS Highlight。検索語と表示変換状態に依存 | ページ内再利用を先行 |
| 個人ハイライト・メモ | 既存の個人保存レコードを利用 | Range復元と照合。共通法令データに個人情報を混ぜない | 別管理 |
| ブックマーク・閲覧位置 | 既存保存データを利用 | ボタン・イベント・現在の座標を作り直す | 別管理 |
| 目次・コピー・法令名整形 | 必要なら中立な文字列・構造 | 操作時のUIとURL生成。初期速度への効果は小さい可能性 | 低 |
| 幅・濃さ・表示トグル・ポップアップ | 保存解析とは分離 | 現在の設定を適用 | 解析キーに原則含めない |

定義抽出自体は他法令本文の取得や外部参照データには依存しない。ただし、可視条文・DOM候補・単一テキストノード内での一致・数字／かな変換後の文字列に依存する。現在の処理順による結果差をなくす前に「XMLだけで常に同じ結果になる」と扱わない。

## 5. 実装する場合の設計案

### 5.1 先に入力と適用を分離する

1. 通常の条文表示かを確認し、URL文脈・可視改正IDラベル・本文世代を取得する。
2. 一度の走査から、scope付き条項索引・基準テキスト・ネイティブリンクを作る。拡張のspanやボタンは入力から除く。
3. 索引を共有して定義・内部参照を解析する。Elementを保持する表示用オブジェクトと、保存用JSONを分ける。
4. キャッシュhit時もscope付き出典キーから現DOMへ再結合し、一致を検証する。DOM・設定・版が変わったら旧処理を取り消す。
5. miss・破損・保存不可の場合は通常解析を使う。途中結果を完成レコードとして保存しない。

静止時間だけでは全文完成を証明できない。安定待ちを使う場合も、後続本文変更で候補を無効化し、再計算・再結合できることが必要。完成信号が確立できない間は、レコードに入力ダイジェストを必須とし、部分結果は暫定扱いにする。

### 5.2 キーと保存内容

```text
context = {
  lawId, displayedRevisionId|null, occasionDate|null,
  viewMode: "text", domAdapterVersion
}
inputDigest = SHA256(orderedRecords[
  scope, id, parentKey, normalizedText, semanticStructure,
  nativeLinks[textPosition, anchorText, resolvedTarget]
], selectedProvisionSet)
analysisKey = [kind, schemaVersion, processorVersion, context, inputDigest]
```

相対hrefはその表示版のURLで解決する。同じ `#条項ID` でも版の文脈が違うため、href文字列単体のハッシュでは不十分。DOMラベルから版を解決できない場合も、法令IDだけを版と見なさず、URL文脈と内容ダイジェストを残す。

```text
definitions: [{term, definition, sourceKeyWithScope, sourceType, targetDepth}]
internalReferences: {targetKeyWithScope: {externalLawSources: [...]}}
provisions: [{keyWithScope, id, parentKey, normalizedText, label}]
```

定義辞書や参照元文には整形済み文字列が含まれるため、抽出だけでなく本文整形規則のバージョンも失効要因になる。定義0件は、入力が確定している場合には有効な結果として保存する。

保存先はbackground経由の拡張機能側IndexedDBを候補とする。content scriptでサイトの保存領域に直書きする設計は避ける。保存上限は件数とバイト数を管理し、再訪時刻によるLRUを検討する。現Liteの100件・保存時刻順削除を、そのまま解析キャッシュの容量設計とはしない。

### 5.3 無効化を分ける

- 本文・条項構造・リンク先・表示対象・表示版・解析規則：対応する本文解析を失効。
- 同じ入力のDOM作り直し：保存解析は再利用し、Element・Range・イベントを再結合。
- 外部参照取込／削除／同梱更新：外部参照と統合結果だけ失効。内部参照と定義辞書は維持。
- 定義ON/OFF・クリックのみ・逆参照internal/external/both・括弧濃さ：表示適用を変更。OFFや切替で実行中の処理を中断。
- 数字／かな変換：基準データを維持して表示との対応を更新。現DOMを解析入力とする暫定実装なら変換状態もキーに加える。
- 個人メモ・色・ブックマーク：個人表示を更新し、共通本文解析は維持。

## 6. 性能評価の判断と未測定事項

実行した既存検証は `node --test tests/lite-loading.test.cjs` の7件で、すべて成功した。同時要求の共有、版解決失敗時の取得、タイムアウト、同じキーで本文が変わった際の再描画等を確認するテストである。通常モードの統合・性能を保証するものではない。調査用再現検証は8件すべてで想定した現挙動を確認した。

加工キャッシュの収支は次で判断する。

```text
hit時の純短縮時間
  = 省けた抽出・解析時間
    - 追加の基準化・ハッシュ・DB読込・転送・JSON処理・DOM再結合時間
```

基準化・索引作成をもともとの解析と共有できれば、追加費用を減らせる。定義辞書だけの保存では、本文全体の用語検索とspan作成が残る。内部逆参照の保存でも、対象索引と番号の補完・クリック化は残る。idle実行は待ち時間の配置を変えるもので、同期走査を自動的に短くはしない。

次の計測は、拡張機能を導入した専用ブラウザと一時的な計測フックが必要なため今回は実施していない。製品コードは変更せず、速度値は推測で埋めていない。

| 計測対象 | 分離して記録する値 |
|---|---|
| 初期表示 | 本体の本文利用可能時刻、拡張初期化待ち、idle待ち、各機能の適用完了 |
| 定義 | 候補構築・本文整形・抽出、出現検索、span作成・適用 |
| 逆参照 | 外部読込、内部収集、統合、索引構築、DOM適用 |
| 個人データ | ハイライト件数と復元時間、ブックマーク復元 |
| hit/miss比較 | ハッシュ、DB、メッセージ転送、再結合、総時間、最長同期処理、保存容量 |

同一法令・同一設定で初回と再訪を分け、短い法令・長い法令・定義多数・附則多数を対象とする。現在版／過去版、比較表示への切替、待機中OFF、本文訂正、hrefだけ変更、部分差替え、外部取込、キャッシュ破損も別に確認する。環境・実行順・反復回数を記録してから改善率を出す。

今回の環境ではブラウザから実サイトを観察できた一方、シェルから公式サイトへのHTTP取得は名前解決に失敗した。Web取得ツールでも配信JS本文とAPI仕様YAMLの取得に成功していない。このため本体の配信ソース・要求応答・完成通知の解析は未完了。内部APIの名前とDOM観察を、その代わりの確定仕様とは扱っていない。

## 7. 推奨順序

1. scope付きキー、通常表示の識別、本文世代、待機後の再確認とキャンセルを設計する。
2. 基準本文・条項索引を共有し、上記の区間を実測する。
3. 収支が合う場合に定義辞書・内部参照JSONの保存を導入する。
4. DOM適用が支配的なら段階適用・分割実行を優先し、必要に応じて出現位置保存を追加する。

通常モードの本文通信を省略する変更や、e-Gov本体の内部APIへの介入は、この後加工キャッシュとは別の検討である。本調査では実装していない。
