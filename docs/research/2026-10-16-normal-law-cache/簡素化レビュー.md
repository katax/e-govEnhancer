# 実装設計案の簡素化レビュー

レビュー日：2026-10-16（日本時間）

検証後の追記：別紙 [簡素案検証結果](簡素案検証結果.md) に実ブラウザでの復元・性能検証を記録した。全文二重照合は費用が高く、待機中だけの変更監視を候補とする。また、本レビューの加工キャッシュでは本文ダウンロードは省けない。再訪時の体感改善には本文取得経路の評価を優先する。

## 結論

**前案は初期実装として大きすぎる。既存の解析・DOM適用の間に、小さなキャッシュを挟む案から始める方がよい。**

目的は、再訪時に同じ定義抽出・内部逆参照解析を繰り返す費用を減らすこと。前案は、これに本文の共通モデル、解析処理の改造、全機能の変更監視、出典移動の仕様変更まで含めていた。性能効果がまだ分からない段階で、必要以上の前提作業を作っている。

ただし、簡素な案で同じ速度改善を得られることは未検証。キャッシュの一致条件を厳しくして作り込みを減らす代わりに、再利用の機会が減ることを受け入れる案である。初回表示やDOMマーク作成自体の高速化は、どちらの案でも別に評価する必要がある。

## 1. 前案のどこが過剰だったか

| 前案 | 初期版での見直し |
|---|---|
| 切り離しDOM、正規化トークン列、共通条項レコードを新設 | 既存のDOM解析を維持する。まず現在の入力を厳密に照合する |
| 定義に新しいscope付きキー＋role＋出典ハッシュを持たせる | 再利用時の復元は、まず元要素の完全なDOM IDで足りるかを試す。一意でなければ再解析 |
| 内部逆参照を新しい保存形式へ変換し、表示前に戻す | 既にJSON化可能な既存結果をそのまま保存する |
| 専用IndexedDBと3つの新規共有モジュール | 小容量なら既存権限で使える `chrome.storage.local` を候補にする |
| schema／processor／adapter／textPolicy等を個別管理 | 初期版は一つの `cacheVersion`。関連変更時にまとめて失効 |
| 読むたびに更新するLRU、payloadの追加ハッシュ | 小さな上限と保存日時順の削除、型・内容の検証から始める |
| 全機能の自己変更を記録する共通管理層 | キャッシュの非同期処理前後の確認を先に実装。監視の不備は必要な箇所を別に修正する |
| キャッシュと同時に定義markを分割実行 | 最初は既存の適用を維持。markが重いと測定できてから分割する |
| 過去版のポップアップや参照元移動も変更 | 別の正確性修正として切り出す。保存の導入と混ぜない |
| 多数の状態・独立した完了条件・固定の時間閾値 | 機能別の実行番号、入力照合、失敗時の再解析に絞る。数値は測定後に決める |

全体の変更監視や版を保つ移動が不要という意味ではない。**キャッシュを追加するために、すべてを一度に直す必要があるか**を切り分ける。

## 2. 現コードから確認できる、簡素化の根拠

### 定義のDOM参照は一つにまとめて保存できる

`content.js:4251` の `addDefinition()` は、次の3つへ同じ `targetEl` を入れている。

```js
anchorEl: targetEl,
sourceEl: targetEl,
excludeEl: targetEl
```

したがって保存時は `sourceId: targetEl.id` に置き換え、読み込み時に現在の本文内でそのIDを持つ唯一の要素を探せば、3つとも復元できる。完全なDOM IDには附則・条・項・号の情報も含まれる。新しい共通出典キー体系は、これだけのためには必要ない。

定義レコードの他の既存値 `term/definition/key/targetDepth/sourceType` はそのまま保存できる。IDなし、本文外、一致なし、重複IDの場合は、その定義キャッシュ全体を使わず既存の抽出を実行する。

この方法は附則の候補抽出バグそのものを直さない。`buildDefinitionCandidateCache()` が条番号だけで候補をまとめる問題は、既存の `parseProvisionHash()` でscopeを加える小さな修正として別に扱える。保存済み個人データやジャンプ履歴のキーを作り直す必要はない。

### 内部逆参照は既に保存に向いた形で返る

`shared/egov-shared.js:659` の `collectInternalLawReferences()` は、文字列・配列・オブジェクトで構成された結果を返す。解析中のWeakMapは戻り値に含まれない。

その戻り値を保存し、hit時は既存の `mergeLawReferences()` と `applyReferenceLinksForLaw()` へ渡せる。新しいtarget/source形式へ変換して戻す層は初期版では不要。外部参照との統合結果は保存しない。

### 別のDBが必須という根拠はまだない

この拡張は既にStorage APIを使っている。公式資料では、Storage APIはcontent scriptとservice workerの双方から利用でき、`storage.local` は通常10MBの上限を持つ。少量の試験導入で、最初から専用DBが必要とはいえない。[Chrome公式Storage API](https://developer.chrome.com/docs/extensions/reference/api/storage)

ただし、この領域は既存のメモ等とも共有する。キャッシュ用の小さい総容量上限・1件上限を設け、個人データのための余裕がない場合は保存を見送る。大きい法令の結果が上限に収まらない、または実測で費用が高い場合にIndexedDBへ進む。

## 3. より小さい構成案

```text
既存の解析開始地点
  → 現在の入力を識別
  → 同じ入力の保存結果があるか確認
  → あれば復元、なければ既存関数で解析
  → 既存の関数でDOMへ適用
  → 解析結果を保存
```

定義と内部逆参照は別々に包む。共通の解析基盤を先に作る必要はない。

保存単位の例：

```js
// 各法令・各機能につき、最後に保存した入力の結果を1件持つ。
storageKey = `normalAnalysis:${kind}:${lawId}`;
record = {
  cacheVersion: 1,
  fingerprint: "...",
  savedAt: 0,
  data: /* 定義の配列、または既存の内部逆参照結果 */
};
```

同じ法令の過去版と現行版が保存枠を上書きし合うことは許容する。fingerprintが一致しなければ必ずmissなので、正しさには影響せず、ヒット率だけが下がる。複数の版を大量に保持する仕組みは、利用実態が分かってから追加する。

content側で1件を読み、書き込みと容量整理だけをbackgroundへ集約すればよい。backgroundは書き込みを順番に処理し、保存日時が古い自分のキャッシュだけを削除する。読み取りでアクセス日時を更新しない。既存の個人データを削除対象に含めない。

変更の中心は `content.js` と `background.js`、必要なテストになる。コード量に応じて保存用ファイルを一つ分ける程度でよく、最初から3つの共有モジュールへ分解しない。

## 4. 入力照合も、まずは厳しく単純にする

前案は、拡張の加工を取り除いた共通本文を作り、異なるDOMでも同じ入力として再利用できるようにしていた。これはヒット率の向上に役立つが、透明化する要素や維持する構造を正確に定義する負担が大きい。

初期版の比較候補は、**解析直前のDOM表現をそのまま照合する方式**でよい。

```text
fingerprint = hash(JSON.stringify([
  cacheVersion, kind, lawId, lawTitle, baseUrl,
  通常表示であること,
  表示対象の条文ID列,
  解析対象rootのinnerHTML,
  解析結果に影響する表示変換状態
]))
```

HTMLは照合用に一時的に読むだけで、保存・再挿入はしない。保存するのはハッシュと解析結果である。構造やhrefも含まれるので、「文字列は同じだがリンク先だけ違う」入力を別にできる。

成立条件と制限：

- 定義の既存抽出はdocument全体の候補と可視条文を参照する。本文外に解析対象が存在する入力では、root内HTMLだけで足りないため、初期版のキャッシュを迂回する。本文内の可視対象も別に照合する。
- URLは実際に解析へ渡す値を含める。法令名も内部参照の戻り値に入るため照合対象にする。
- 定義キャッシュの確認は既存の定義markを解除した後、再mark前に置く。内部参照は既存の内部解析開始地点で確認する。
- 他機能のspan、ボタン、括弧グループID等でHTMLが変わったらmissにする。無理に同一視しない。
- 数字・かな変換後や、比較表示、重複ID等の対応外入力は迂回する。
- 自身の `#provisionview` 属性も解析入力に影響する場合は、innerHTMLだけでなく該当属性を照合へ加える。

これで再利用の機会が少なすぎるなら、**実際にmissを引き起こす要素だけ**を後から除外する。最初から汎用の正規化DOMを構築しない。

全文のHTML取得とハッシュにも費用がある。この方式が速いとはまだ断定しない。初回抽出が十分速ければ、キャッシュ自体を追加しない判断も残す。

## 5. 削ってはいけない確認

簡素化しても次は残す。

1. **入力と処理版の一致。** 法令ID・改正IDだけではhitさせない。0件結果とmissも区別する。
2. **非同期処理後の再確認。** 保存読込やハッシュ計算の間に本文が変わる可能性がある。適用直前にroot・URL・入力・有効設定を再確認し、不一致なら保存結果を捨てる。
3. **現在のElementへの復元。** 定義の完全IDを本文内で一意に解決する。保存したHTMLや旧Elementを戻さない。
4. **失敗時の通常解析。** 保存なし、形式不正、容量不足、結合失敗を表示失敗にしない。結果の型検証は省略しない。
5. **古い処理の適用防止。** 定義は機能ごとの実行番号を一つ追加し、逆参照は既存の `referenceAnalysisGeneration` を活用する。逆参照バッチの `isEnabled` 判定にも実行番号を含める。

同じDOM表現で中のElementだけ置き換わった場合もあるので、await前に取得したElementを使い回さず、hitの検証後に現DOMで復元する。

一方、キャッシュを読み終わった後の動的本文追従は、既存の変更監視にもともとある課題である。今回の簡素案がそれを全面解決するとは扱わない。本文訂正・hrefだけ変更・root置換の試験から必要な監視修正を絞り、保存OFFにも同じ修正を適用する。前案の全書き込み記録方式を唯一の解決策としない。

## 6. 着手順も小さくする

1. **抽出・マーク・内部参照解析の時間を分けて測る。** 現コードの定義ログはextractとmarkの合計なので、保存できる部分の大きさが分からない。
2. **節約額の大きい方から薄くキャッシュを追加する。** 実装の容易さでは内部参照が有利だが、実際の優先度は計測で決める。定義も同じ包み方で続ける。
3. **初回／再訪の総時間と結果一致を確認する。** HTML取得・ハッシュ・読込・復元も含める。
4. **困った箇所だけ拡張する。** ヒット率が低ければ限定的な正規化、容量が足りなければIndexedDB、markが重ければ分割実行を検討する。

これは定義キャッシュを目的から外す提案ではない。最終的な対象は定義と内部参照の両方のまま、同時に基盤全体を作ることをやめる案である。

最初の検証は、同じ入力のhitとmiss、本文／hrefだけ変更、待機中OFF、root置換、附則の出典復元、形式不正・保存失敗に絞る。必要な正確性の検証は維持し、最初から大きなベンチマーク機構や全機能の再実装を用意しない。

## 推奨判断

前案をそのまま実装するのは勧めない。まず「既存解析を維持する小さなキャッシュ」を候補とし、測定で有効性を確認する。入力を完全一致させる費用が抽出費用以上なら、保存を導入せず重い部分そのものを改善する。

本レビューは設計と現コードの照合による評価である。簡素案の実装、ヒット率の確認、速度測定は行っていない。製品コード・既存テストは変更していない。
