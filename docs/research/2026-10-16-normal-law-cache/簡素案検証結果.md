# 簡素案の検証結果と、速度改善の対象の整理

検証日：2026-10-16（日本時間）

## 結論

**既存の定義・内部参照解析を残して結果だけ再利用する、小さい構成は成立した。ただし、今回検証した加工キャッシュはe-Govからの本文ダウンロードを省かない。再訪時の表示待ちを大きく減らす目的には、本文取得・本体描画の経路を別に評価する必要がある。**

ユーザーから「速度改善はダウンロード省略によるのでは」と指摘があった。ここまでの設計・検証は加工の再計算へ寄りすぎていた。以下のCPU測定を、本体ダウンロードを含む体感改善の根拠としては扱わない。

## 1. ダウンロードの省略と加工の省略は別

| 経路 | 初回表示前の本文通信待ち | 裏での本文再取得 | 拡張の解析 |
|---|---|---|---|
| 現在の通常モード | 本体の取得・描画を待つ | 本体の実装とブラウザキャッシュに依存 | 本文DOMから実行 |
| 今回の加工キャッシュ案 | 上と同じ | 上と同じ | 保存結果があれば一部省略 |
| 現在のLiteでXML cache hit | 保存XMLを先に表示できる | XMLを取得して内容を確認する | Lite側で描画・加工 |

`viewer.js:1592` はネットワーク取得要求を開始し、その完了を待たず `1602` で保存XMLを読む。`background.js:827` の本文取得は `cache: 'no-store'` である。したがって現在のLiteは、cache hit時に**表示のための通信待ちを外す**仕組みを既に持つが、**本文ダウンロード自体を常に省く**仕様ではない。

通常モードは `manifest.json:56` の `document_end` で注入され、`content.js:7480` の初期化後に本体DOMを加工する。後加工の保存だけでは、本体が先に行う取得を止められない。

ダウンロード省略を目的にする場合の検討対象：

- 独自表示を許容するなら、既存Liteの保存XML先行表示を基準に、再取得頻度・更新確認・表示準備の費用を測る。
- 通常モードの画面を維持するなら、本体が読む前にキャッシュ済みデータを渡す等の別設計が必要。現在のcontent scriptへ結果保存を追加するだけでは達成しない。
- 本体のHTTPキャッシュが既にどの程度効くかも未計測。ダウンロードが最大の待ち時間と断定するには、通信・描画・後加工の時間を分ける必要がある。

改正IDが同じでも本文訂正の可能性を考慮している現コードを踏まえ、ダウンロードを省く条件は、内容の最新性をどのように確認するかとセットで決める。法令IDや改正IDだけを根拠に無期限に再取得を止める提案ではない。

## 2. 今回実行した検証

- 実Chrome `155` 系で、製品の `content.js` と `shared/egov-shared.js` の実関数を実行した。起動部分だけをメモリ上のテスト用コピーで差し替え、製品ファイルには書き込んでいない。
- 固定データは、旧形式のarticle／paragraphと新形式のsection／ArticleTitleを模した合成DOM。実サイトで観察したcolumn等の構造も含めたが、法令全文をダウンロードしたデータではない。
- 定義5語の26／242／802条文、定義241／801語の242／802条文を使用した。各条件はウォームアップ2回後に10回測り、保存OFF／miss／hitの実行順を交互にした。
- キャッシュのデータはJSON化してメモリへ保存・復元した。実 `chrome.storage.local` の待ち時間、IPC、容量制限、backgroundとの統合は測定に含まない。
- 実保存APIも隔離した一時Chromeプロファイルで確認を試みたが、検証用拡張ページが `ERR_BLOCKED_BY_CLIENT` となり測定できなかった。利用者のブラウザプロファイルは変更せず、一時プロファイルは終了後に削除した。
- 関連する既存Lite DOMテストは7件成功、過去ソースとの任意比較1件は未指定のためskip。

## 3. 復元と入力変更の検証

2方式それぞれで27項目を確認した。成功はプロトタイプのこの範囲の確認であり、通常モードの製品組込み完了ではない。

| 確認した項目 | 結果 |
|---|---|
| 定義A/B/C/Dの保存・復元 | 定義の値、出典要素、mark後HTMLが保存OFFと一致 |
| 定義の出典ID | 現DOMで復元でき、anchor/source/excludeが同じ現在要素になった |
| 附則の出典 | 完全IDで附則要素へ復元できた |
| 内部逆参照JSON | 保存前後のJSONとクリック化後HTMLが一致 |
| 実際のクリック | 復元した定義のツールチップと参照元ポップアップが開いた |
| 本文・hrefだけ変更 | 以前の保存結果を使わずmiss |
| 待機中OFF・新ジョブ開始 | 古い結果をキャンセル |
| 待機中の文字変更・root置換 | 古い結果を破棄 |
| 重複ID・本文外の候補・比較表示・文字変換済み | 対象外として通常解析へ迂回 |
| 壊れたJSON・存在しない出典ID・旧処理版 | 保存結果を使わず再解析 |
| 読込失敗・保存失敗 | 通常解析の結果を取得できた |
| 定義0件 | 0件を有効な保存結果として再利用できた |
| 無関係なボタン・括弧ラップ追加 | 生のHTML照合なのでmiss。誤再利用はしないがヒット率を下げる |

本文内の要素を同じHTMLで差し替えた場合、既存 `getAllArticles()` の配列に旧Elementが残り、厳密照合方式はそのままでは再利用を見送った。配列を無効化すれば新Elementへ復元できた。後述の短時間監視方式では、同じHTMLでも差替えがあれば保守的に古い結果を捨てる。

## 4. 最初の簡素案は、照合が高くついた

HTML全体から入力を作り、非同期読込の後にも同じ入力を作り直して比較する方式を試した。

802条文・定義5語・旧DOMの中央値：

| 処理 | 保存OFF | hit | miss |
|---|---:|---:|---:|
| 定義解析＋markのDOM操作 | 60.50ms | 65.70ms | 76.70ms |
| 内部参照の解析部分 | 19.10ms | 17.15ms | 38.00ms |

定義では保存通信を省いた条件でも逆効果だった。別に費用を分解すると、この規模で入力の捕捉が約5～6ms、ハッシュが約2～3ms、再照合の捕捉が約5msだった。捕捉には候補探索、IDの重複確認、HTML直列化等を含む。原因をハッシュ計算だけに帰すべきではない。

## 5. 全文の二重確認を、待機中だけの監視へ置き換えた

次の小修正も試した。

```text
一時的なMutationObserverを接続
  → 入力を一度捕捉してハッシュ化
  → 保存結果を読む
  → 未処理の変更記録を回収して監視を外す
  → 変化があれば結果を捨てる
  → 変化がなければ現在要素へ復元し、既存処理で適用
```

監視するのは読込待ちの短い区間だけ。DOM変更があれば、自分や他機能による変更も含めて再利用を見送る。自分のmark開始前に監視を終えるため、全書き込みの記録層や汎用スナップショットを用意する必要はなかった。root・URL・有効設定・実行番号の確認も残した。

この方式でも27項目を確認した。ただし、適用後の変更追従や全バッチのキャンセルまで製品へ組み込んだ検証ではない。CSSOM変更等、DOM変更通知のない可視性変化もこの実験では扱っていない。

修正方式の中央値：

| 条文数／定義数 | 処理 | 保存OFF | hit | miss |
|---|---|---:|---:|---:|
| 242／5、旧DOM | 定義＋mark | 17.65ms | 16.80ms | 20.95ms |
| 802／5、旧DOM | 定義＋mark | 59.50ms | 58.90ms | 70.40ms |
| 802／5、新DOM | 定義＋mark | 56.05ms | 56.85ms | 66.25ms |
| 802／801、旧DOM | 定義＋mark | 39.10ms | 32.25ms | 51.25ms |
| 242／5、旧DOM | 内部参照解析 | 5.80ms | 3.65ms | 9.45ms |
| 802／5、旧DOM | 内部参照解析 | 19.85ms | 11.30ms | 31.70ms |
| 802／5、新DOM | 内部参照解析 | 18.80ms | 11.40ms | 29.05ms |

定義が少ない場合はmarkが残るため効果がほぼない。定義が多い場合と内部参照解析には、保存通信費用を除いた短縮余地が見えた。ただしmissは遅くなる。例えば802条文・旧DOMの内部参照では、中央値ベースの粗い収支は、保存通信を0と仮定してもhit率が約6割を超える必要がある。

これらは合成DOMにおけるJavaScriptとDOM操作の時間であり、e-Govの通信、実ページのCSS・描画、実保存APIを含む体感時間ではない。10回の測定で数百μsの差を有意な改善とは扱わない。

## 6. 実サイトで確認した入力の安定性

行政手続法の同一URL・同一改正IDについて、最後の本則条文が表示された後に本文rootのHTMLを取得し、1回再読み込みして厳密に比較した。両方87,830文字で完全一致した。

したがって、生HTMLを入力照合へ使うことが必ず失敗するわけではない。ただし拡張なし・1法令・1回の観察であり、実際のヒット率の証拠にはならない。拡張のUI・括弧処理等でmissになることは固定DOM検証で確認している。

## 7. 判断の更新

- 保存結果からの復元に、共通本文モデルや新しい出典体系は必須ではなかった。
- HTML全体の二重照合は初期案として採用しない。加工キャッシュを作る場合は、短い待機区間の変更監視がより小さい候補になる。
- **加工時間を減らす範囲に限れば**内部逆参照を先行させる余地がある。ただしユーザーの体感改善の主目的に対する優先順位とは分ける。
- **次に評価すべき中心は、本文のダウンロード待ちと本体描画をどこまで避けられるか。** 既存Liteのキャッシュ先行表示と通常モードを、本文が読めるまでの時間で比較する方が目的に近い。
- 実保存APIの費用と実サイトのヒット率を測らずに、保存方式の採用や既定有効化を確定しない。
