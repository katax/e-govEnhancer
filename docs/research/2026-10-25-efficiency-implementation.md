# 処理効率レビューの実装結果

2026-10-25のレビューで挙げた8項目を実装した。作業開始前の変更は維持している。

## 実装

1. 同梱参照データを256分割。通常表示・Lite表示で必要な分割ファイルだけ取得する。全3,868法令の元データとの一致を検証した。分割ファイルの平均サイズは約0.31MB、最大約2.61MBで、従来の95.99MBの全体解析を避ける。
2. キャッシュのサイズ・アクセス日時をメモリ内で再利用。キー一覧は外部削除検出のため確認するが、既知エントリのResponse再取得を省略し、容量超過時だけソートする。別コンテキストからの書き込みは更新識別子で検出し、Web Locksで競合を防ぐ。
3. アクセス日時による本文再書き込みは、各エントリについて最大1分に1回。Liteの再JSON化も削除。ダウンロード日時・期限判定・本文整合性検証は維持する。再起動や別コンテキストの書き込み後は、直近1分のアクセス順が近似になる。
4. ハイライト復元の分割待機を成功件数ではなく試行件数で制御。全件失敗時にも25件ずつ処理を区切る。
5. 法令検索の通信・中止・要求管理を共有。実行中の同一検索を共有し、古い応答を反映しない。入力変更・画面終了時に不要な検索を中止する。日本語入力確定時のcompositionendとinputによる二重検索も抑制する。
6. Lite表示で使っていなかったXML全文再シリアライズと署名計算を削除。
7. フッターの探索・表示判定を関連DOM変更やリサイズ時に限定。差し替え・別フッターへの切り替えは維持する。
8. XML文書ごとに附則の所属を一度だけ索引化。WeakMapにより破棄済み文書を保持しない。

## 分割データの更新と配布

元データを更新したら、次の順に実行する。

```powershell
node tools/build-reference-shards.mjs
./tools/package-extension.ps1 -OutputPath release/new-package.zip
```

元データは作成用の入力としてdata/references.jsonに残す。配布ZIPには分割ファイルだけを収録し、巨大な元データとの二重収録を避ける。オプション画面のエクスポートでは分割ファイルを8件ずつ読み、従来と同じ完全な参照JSONを作る。

パッケージ作成時は元データと全256ファイルのSHA-256を確認し、更新漏れ・欠落・破損があれば停止する。

## 検証

全体テストは82件中81件通過、失敗0件。変更前の比較用ソースが必要な既存テスト1件はスキップ。JavaScript / MJSの構文確認17ファイルと配布ZIP作成・収録検査も通過した。

- 100件の連続キャッシュ保存で、保存済みResponseの照会は0回。再起動後は100件を一度再構築し、その後の保存で再照会しない。
- 20秒間に20回読み出しても本文の書き込みは最初の保存1回のみ。60秒後にアクセス日時を保存してもダウンロード日時は変わらない。
- 別コンテキストによる同じキーのサイズ変更後も容量制限を守る。
- 通常・Liteとも125件の復元試行を5回のフレーム待機に分割。全件失敗と25件成功・100件失敗の両条件を確認。
- 附則100件のXMLで附則一覧の検索は1回。XML全文の再シリアライズは行わない。
- 無関係な画面更新でフッターの再検索・レイアウト照会は0回。フッターの非表示・差し替えでもコントロールを維持する。
- ブラウザ上で新旧検索応答の逆転、入力クリア後の応答、日本語1文字の確定後の検索を確認。
- 同梱データの全件一致とエクスポート結果の一致を確認。

これらは回帰・処理回数の検証であり、実サイトの回線条件を含む表示時間のベンチマークではない。
